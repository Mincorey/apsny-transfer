### К-3. Перенос базы по `MOVING_CHECKLIST.md` потеряет все права доступа

**Где.** `MOVING_CHECKLIST.md`, раздел 4:

```bash
pg_dump ... --no-owner --no-privileges --schema=public --schema=auth --schema=storage
pg_restore ... --no-owner --no-privileges
```

**В чём дело.** `--no-privileges` значит: в дамп не попадает ни один
`GRANT` и `REVOKE`. А на них держится почти вся защита проекта — полтора
десятка миграций только этим и занимались: телефоны и мессенджеры закрыты
правами на колонки, `publish_ride_paid` и `finish_auction` доступны только
серверу, `rating` и `trips_count` клиент менять не может.

На новом сервере таблицы и функции будут созданы заново, и получат права
**по умолчанию для Supabase** — а они у Supabase такие: `anon` и
`authenticated` получают всё на всё в схеме `public`. То есть сразу после
переезда:

- телефоны, Telegram, WhatsApp всех пользователей читаются без входа;
- `publish_ride_paid` может вызвать любой — публикация без оплаты;
- любой пользователь может переписать себе рейтинг и статус поездки.

Сайт при этом будет работать как обычно — заметить нельзя, пока не проверишь.

**Вторая проблема того же места.** Восстанавливать схемы `auth` и `storage`
целиком поверх свежего self-hosted Supabase нельзя: GoTrue и Storage при
первом запуске уже создают свои таблицы своих версий, и восстановление
либо упадёт на конфликтах, либо оставит структуру, не совпадающую с
версией сервиса.

### В-7. Платёжные записи удаляются вместе с поездкой

### В-13. Любой вошедший может заменить чужой аватар и фото машины *(новое, по бою)*

**Где.** Политики Storage на боевой базе, бакет `avatars`:

| Политика | Действие | Условие |
|---|---|---|
| Public can read avatars | SELECT | `bucket_id = 'avatars'` |
| Authenticated users can upload | INSERT | `bucket_id = 'avatars'` |
| Authenticated users can update | UPDATE | `bucket_id = 'avatars'` |

Проверки владельца нет ни в одной. Файлы лежат по пути `<id пользователя>/avatar.jpg`,
id пользователей публичны. Значит, любой зарегистрированный может
загрузить **поверх чужого** аватара или фото машины что угодно — одним
запросом `upload(..., { upsert: true })`. Интерфейс этого не даёт, API —
даёт.

Сам бакет без ограничений: `file_size_limit = NULL`, `allowed_mime_types = NULL`.
То есть туда же можно положить файл любого типа и размера — и он будет
отдаваться публично с домена сервиса. Ограничение «до 5 МБ» и сжатие
существуют только в браузере (`Profile.tsx`), а `compressImage` не-картинки
пропускает как есть.

Политики на удаление нет вообще, поэтому `storage.remove(oldPath)` в
`Profile.tsx` (замена и удаление фото машины) молча не срабатывает — старые
файлы копятся.

пропадут (см. В-5, К-3).

вставки. Две ставки в последние секунды аукциона: транзакция B начинается
на миллисекунду раньше A, но ждёт блокировку, которую взяла A. A вставляет
ставку, B — следом, уже по новой цене, но с **более ранним** временем. Для
базы «последней» окажется ставка A, хотя B её перебила: победителем
назначат не того, а B может получить отказ «дождитесь другого участника».

Вероятность мала (нужны две ставки в одну и ту же долю секунды), но это
ровно конец аукциона, когда так и бывает. Найдено на тестах: внутри одной
транзакции все ставки получают одинаковое время, и победитель выбирается
случайно.

- [x] В `place_bid` и `accept_current_price` записывать `created_at = clock_timestamp()` (реальное время вставки, уже под блокировкой строки поездки); либо добавить в `bids` возрастающий номер (`bigint generated always as identity`) и сортировать по нему — сделано значением по умолчанию колонки `bids.created_at` — код и тест готовы 03.10.2026, ждёт применения на бою
- [x] Тест: две ставки в одной транзакции → победитель — вторая (без миграции тест падает — проверено)

## 7. Что сделано хорошо

Чтобы не потерять при правках:

- Приватность контактов — на уровне прав на колонки и `SECURITY DEFINER`-функций, не в интерфейсе.
- Денежная функция `publish_ride_paid`: блокировка строки, идемпотентность по статусу и по `operation_id`, проверка недоплаты, оповещение.
- Ограничения на числа и длины — в самой базе (`CHECK`), а не только в форме.
- Все функции (кроме двух функций чистки, см. К-2) с явным `search_path`.
- Вебхук ЮMoney: подпись, тестовые уведомления, валюта, `unaccepted`, внятные ответы для повторов.
- CSP без `unsafe-inline` для скриптов — редкость; скрипты вынесены в файлы ради этого.
- Лимит частоты в форме обратной связи, экранирование HTML в Telegram.
- Нагрузочный тест с замерами и выбор сервера по ним.
- Лента выбирается индексом за 0,4 мс на объёме «год работы».
- **На бою:** у `anon` нет права ни на одну изменяющую функцию; служебные функции (`finish_auction`, `publish_ride_paid`, `tg_notify`, чистки) доступны только серверу; у всех функций задан `search_path`.
- **На бою:** целостность данных без единого расхождения; `pg_cron` — ноль сбоев за 30 дней; секреты Telegram лежат в Vault, а не в коде.
- Развёрнутый вебхук (версия 5, `verify_jwt: false` — правильно для внешних уведомлений) совпадает с репозиторием байт в байт.

## 8. Эквайринг Т-Бизнес: план интеграции

Серверная основа (`payments`, `start_ride_payment`, `publish_ride_paid`,
`force_ride_draft`, чистка черновиков) переиспользуется. Пишется:
инициация платежа, приёмник уведомлений, экран оплаты.

### 8.1. Схема

```
[Опубликовать] → Edge Function tbank-init (с токеном пользователя)
                   ├─ rpc start_ride_payment(ride)  → метка (OrderId)
                   ├─ POST https://securepay.tinkoff.ru/v2/Init
                   │     TerminalKey, Amount=10000 (копейки!), OrderId=метка,
                   │     Description, NotificationURL, SuccessURL, FailURL, Token
                   └─ ← PaymentURL → браузер уходит на страницу банка
Банк → POST tbank-webhook (JSON)
         ├─ проверить Token, TerminalKey, Success, Status
         ├─ Status = CONFIRMED → rpc publish_ride_paid(OrderId, PaymentId, Amount/100, raw)
         ├─ REFUNDED / REVERSED / REJECTED → записать и сообщить в Telegram
         └─ ответ: HTTP 200, тело ровно "OK" (иначе банк будет повторять)
SuccessURL → /payment?ride=…&paid=1 → опрос статуса поездки каждые 2 с, до 60 с
```

### 8.2. Что важно не ошибиться

- [ ] **Пароль терминала — только на сервере** (секрет Edge Function). В браузере его быть не должно ни в каком виде; `Init` зовётся с сервера.
- [ ] **Подпись `Token`:** берутся все параметры **верхнего уровня** (вложенные объекты `Receipt`, `DATA` — не входят), добавляется пара `Password`, всё сортируется по имени ключа, значения склеиваются в одну строку, SHA-256. Для уведомления — то же, из пришедшего JSON без самого `Token`. Булевы значения — строкой `true`/`false`.
- [ ] **Сумма в копейках.** 100 ₽ = `10000`. В `publish_ride_paid` передавать рубли (`Amount / 100`), как сейчас.
- [ ] **Проверять в уведомлении:** `TerminalKey` свой; `OrderId` известен; `Amount` не меньше ожидаемого; `Status = CONFIRMED` для одностадийной оплаты. `AUTHORIZED` — ещё не деньги.
- [ ] **Идемпотентность** уже есть в `publish_ride_paid`; `operation_id` = `PaymentId` банка.
- [ ] **Возвраты** (`REFUNDED`, `PARTIAL_REFUNDED`): статус в `payments` + сообщение в Telegram + аннулирование чека в «Мой налог» (см. 9).
- [ ] **CSP.** Переход на `PaymentURL` через `window.location` политикой `form-action` не ограничивается — достаточно убрать `https://yoomoney.ru`. Если будет виджет/iframe банка — добавить его домены в `frame-src` и `script-src`.
- [ ] **Тестовый терминал** (`…DEMO`) и прогон тест-кейсов банка до боевого.
- [ ] **Тексты:** `PAYMENT_PROVIDER` → «Т-Банк»; оферта, политика, условия, страница платных услуг; `ОПИСАНИЕ-ДЛЯ-МОДЕРАЦИИ-ЮMoney.md` → под анкету Т-Бизнес.
- [ ] **Порядок включения** (исправленный В-8): задеплоить обе функции → проверить на тестовом терминале → боевой терминал → платёж 100 ₽ самому себе → и только потом одной выкладкой: новый интерфейс + `payments-enable.sql`.

Детали протокола сверять по официальной документации:
[инициализация платежа](https://developer.tbank.ru/eacq/api/init),
[уведомления](https://www.tinkoff.ru/kassa/develop/api/notifications/),
[способы интеграции](https://developer.tbank.ru/eacq/intro/connection).
Прочитать страницы документации напрямую из этой сессии не удалось

## 9. ИП на НПД и приём оплаты

Вы — ИП, применяющий налог на профессиональный доход. Это законная и
распространённая схема, и она влияет на три вещи в проекте.

**Реквизиты.** Сейчас в `siteInfo.ts` статус «самозанятый, плательщик НПД» и
только ИНН. Для ИП в оферте и на странице оплаты указываются: ФИО полностью
с пометкой «ИП», ОГРНИП, ИНН, налоговый режим (НПД), контактный email.
Банк при подключении эквайринга сверяет реквизиты на сайте с документами.

- [ ] Поле `ogrnip` в `OPERATOR`, статус «Индивидуальный предприниматель, применяющий НПД»; вывести в оферте, условиях, на `/payment` и в квитанции

**Чеки.** На НПД онлайн-касса (54-ФЗ) не нужна; чек формируется в
«Мой налог». При безналичной оплате его можно сформировать не сразу, а до
9-го числа следующего месяца, но на **каждый** платёж. При возврате чек
аннулируется. Т-Бизнес для ИП на НПД умеет регистрировать доход сам —
это стоит включить, иначе на каждые 100 ₽ придётся заходить в приложение.
Объект `Receipt` в `Init` при этом, скорее всего, не передаётся — он для
онлайн-кассы. **Уточнить у менеджера Т-Бизнес при подключении.**

- [ ] Уточнить у банка автоматическую регистрацию дохода НПД и нужен ли `Receipt`
- [ ] В оферте раздел 3 уже написан под НПД — поправить только название банка

**Ограничения режима.**

- Лимит дохода — 2,4 млн ₽ в год. При 100 ₽ за публикацию это 24 000 публикаций; до лимита далеко, но за ним нужно следить.
- **На НПД нельзя быть посредником** по договорам поручения, комиссии и агентским. Сейчас сервис продаёт **свою** услугу — публикацию, — а за поездку люди рассчитываются между собой напрямую. Это правильно, и так должно остаться: принимать оплату самой поездки через сайт (даже «для удобства», даже как депозит) на НПД нельзя.
- Нельзя нанимать сотрудников по трудовому договору.

Я не юрист и не налоговый консультант. Выше — общие правила, которые стоит
подтвердить у Т-Бизнес при подаче заявки и у бухгалтера.

   `authenticated`, `service_role`; схемы `auth`, `storage`, `cron`, `net`,
   `vault`; функция `auth.uid()` из `request.jwt.claim.sub`; **права по
   умолчанию, как у Supabase** (`anon`/`authenticated` получают всё на новые
   объекты в `public`).
2. `supabase_schema_v2.sql` + все 54 миграции по имени файла (с одной
   перестановкой, чтобы `yoomoney_payments` шёл раньше зависящих от него).
3. Сценарии под ролями через `SET ROLE anon` / `SET ROLE authenticated` и
   `SET request.jwt.claim.sub`.

## Приложение Б. Черновик укрепления функций (К-2 / В-5, проверен на локальной базе)

Не применён никуда. На бою срочности нет (у `anon` права уже отозваны,
`complete_trip` правильная). Текст ниже совпадает с боевым по логике,
плюс явная проверка входа и `IS DISTINCT FROM`; пойдёт в первую миграцию
после наведения порядка (В-5).

```sql
create or replace function public.close_auction_early(p_ride_id uuid) returns jsonb language plpgsql security definer set search_path = public, pg_temp as $$
declare v_ride record; v_winner_id uuid; v_uid uuid := auth.uid();
begin
  if v_uid is null then raise exception 'Требуется авторизация'; end if;
  select * into v_ride from public.rides where id = p_ride_id for update;
  if not found then raise exception 'Поездка не найдена'; end if;
  if v_ride.creator_id is distinct from v_uid then raise exception 'Только создатель поездки может закрыть аукцион'; end if;
  if v_ride.status <> 'active' then raise exception 'Аукцион уже завершён'; end if;
  select bidder_id into v_winner_id from public.bids where ride_id = p_ride_id order by created_at desc limit 1;
  if v_winner_id is null then raise exception 'Нет ставок для завершения аукциона'; end if;
  update public.rides set status='booked', winner_id=v_winner_id, auction_end_time=now() where id=p_ride_id;
  insert into public.notifications (user_id,type,title,body,ride_id) values (v_winner_id,'auction_won','Вы выиграли аукцион!','Поздравляем! Поездка '||v_ride.origin||' → '||v_ride.destination||' ваша.',p_ride_id);
  insert into public.notifications (user_id,type,title,body,ride_id) select distinct b.bidder_id,'auction_lost','Аукцион завершён','По поездке '||v_ride.origin||' → '||v_ride.destination||' выбрали другого участника.',p_ride_id from public.bids b where b.ride_id=p_ride_id and b.bidder_id<>v_winner_id;
  return jsonb_build_object('success',true,'winner_id',v_winner_id);
end $$;
create or replace function public.complete_trip(p_ride_id uuid) returns jsonb language plpgsql security definer set search_path = public, pg_temp as $$
declare v_ride record; v_uid uuid := auth.uid();
begin
  if v_uid is null then raise exception 'Требуется авторизация'; end if;
  select * into v_ride from public.rides where id = p_ride_id for update;
  if not found then raise exception 'Поездка не найдена'; end if;
  if v_ride.creator_id is distinct from v_uid then raise exception 'Только создатель поездки может завершить её'; end if;
  if v_ride.status <> 'booked' then raise exception 'Поездка должна быть в статусе booked для завершения'; end if;
  update public.rides set status='completed' where id=p_ride_id;  -- trips_count считает триггер trg_sync_trips_count
  return jsonb_build_object('success',true);
end $$;
revoke execute on function public.close_auction_early(uuid), public.complete_trip(uuid), public.place_bid(uuid,numeric),
  public.submit_review(uuid,uuid,integer,text), public.accept_current_price(uuid,uuid), public.cancel_ride(uuid) from public, anon;
revoke execute on function public.auto_complete_expired_rides(), public.run_retention_cleanup(), public.cleanup_old_notifications(), public.cleanup_old_cancelled_rides() from public, anon, authenticated;
alter function public.cleanup_old_notifications() set search_path = public, pg_temp;
alter function public.cleanup_old_cancelled_rides() set search_path = public, pg_temp;
```

## Приложение В. Результаты проверки боевой базы (29.09.2026)

**Права на колонки** (что отличается от ожидаемого):

**`pg_cron`:** 4 задачи, активны; за сутки 1440 + 24 + 24 + 1 успешных

**Расширения:** `pg_cron` 1.6.4, `pg_net` 0.20.0 (в `public`), `supabase_vault`

**Нагрузка (`pg_stat_statements`):** самое затратное — сама задача закрытия

## Приложение Г. Проверочные запросы к базе

Раньше лежали отдельным файлом `АУДИТ-2026-09-29-проверка-базы.sql`,
теперь здесь. Только чтение — ничего в базе не меняют. Запускать в
Supabase → SQL Editor по одному блоку. 29.09 уже выполнены (результаты —
раздел 0.1 и Приложение В). Повторять после каждой миграции и
обязательно после переезда (К-3): результаты на новом сервере должны
совпасть с облаком.

```sql
-- ============================================================================
-- АУДИТ 29.09.2026 — проверка боевой базы APSNY-TRANSFER
-- ============================================================================
-- ТОЛЬКО ЧТЕНИЕ. Ни один запрос ниже ничего не меняет.
--
-- 29.09.2026 ВЫПОЛНЕНО через коннектор Supabase — результаты в аудите,
-- раздел 0.1 и Приложение В. Файл оставлен для повторной сверки: после
-- каждой миграции и ОБЯЗАТЕЛЬНО после переезда (пункт К-3) — результаты
-- на новом сервере должны совпасть с облаком.
--
-- Как запускать: Supabase Dashboard → проект uprcnpgmmnvsoxasuhun →
-- SQL Editor → вставить блок → Run. Запускать по одному блоку (1, 2, 3 ...),
-- результат каждого скопировать и прислать — по нему закрываются пункты
-- аудита, помеченные «нужна проверка на боевой базе».
--
-- Зачем. Аудит делался по коду репозитория: база собиралась из миграций
-- на локальном PostgreSQL. Доступа к боевой базе не было, а она местами
-- отличается от репозитория (см. пункт В-5 аудита). Эти запросы показывают,
-- как обстоят дела на самом деле.
-- ============================================================================


-- ─── 1. К-2: кто может вызывать функции ─────────────────────────────────────
-- Смотреть на колонку anon. Для close_auction_early, complete_trip,
-- auto_complete_expired_rides, run_retention_cleanup, cleanup_old_* там
-- должно быть false. true = пункт К-2 подтверждён на бою.
select p.proname                                            as функция,
       has_function_privilege('anon',          p.oid, 'execute') as anon,
       has_function_privilege('authenticated', p.oid, 'execute') as authenticated,
       p.prosecdef                                          as security_definer,
       coalesce(array_to_string(p.proconfig, ', '), '—')    as search_path
from pg_proc p
where p.pronamespace = 'public'::regnamespace
order by 1;


-- ─── 2. К-2 и В-5: тексты функций отличаются от репозитория? ─────────────────
select p.proname as функция,
       pg_get_functiondef(p.oid) ~* 'auth\.uid\(\)\s+is\s+null|v_uid\s+is\s+null'
                                   as есть_проверка_входа,
       pg_get_functiondef(p.oid) ~* 'trips_count\s*=\s*trips_count\s*\+\s*1'
                                   as сама_считает_поездки,
       pg_get_functiondef(p.oid) ~* 'draft'
                                   as знает_про_черновики
from pg_proc p
where p.pronamespace = 'public'::regnamespace
  and p.proname in ('close_auction_early','complete_trip','get_trip_view',
                    'place_bid','cancel_ride','submit_review','finish_auction')
order by 1;


-- ─── 3. В-5: функции, которых нет в репозитории ─────────────────────────────
-- Полный текст — чтобы положить его в миграцию. Прислать целиком.
select pg_get_functiondef(p.oid)
from pg_proc p
where p.pronamespace = 'public'::regnamespace
  and p.proname in ('close_expired_auctions');


-- ─── 4. В-1, В-3, С-1: права на колонки ─────────────────────────────────────
select table_name as таблица, grantee as роль, privilege_type as право,
       string_agg(column_name, ', ' order by column_name) as колонки
from information_schema.column_privileges
where table_schema = 'public'
  and grantee in ('anon', 'authenticated')
  and table_name in ('users', 'vehicles', 'rides', 'bids')
group by 1, 2, 3
order by 1, 2, 3;


-- ─── 5. Все политики RLS ────────────────────────────────────────────────────
select schemaname as схема, tablename as таблица, policyname as политика,
       cmd as действие, roles as роли, qual as условие, with_check as проверка
from pg_policies
where schemaname in ('public', 'storage')
order by 1, 2, 3;


-- ─── 6. С-11: Storage — бакеты и их ограничения ─────────────────────────────
select id as бакет, public as публичный,
       file_size_limit as лимит_байт, allowed_mime_types as разрешённые_типы
from storage.buckets;


-- ─── 7. В-7: что происходит с платежами при удалении поездки ────────────────
select conname as связь, pg_get_constraintdef(oid) as определение
from pg_constraint
where conrelid = 'public.payments'::regclass and contype = 'f';


-- ─── 8. pg_cron: задачи и последние запуски ─────────────────────────────────
select jobid, jobname, schedule, command, active from cron.job order by jobid;

select j.jobname, d.status, count(*) as запусков, max(d.start_time) as последний
from cron.job_run_details d join cron.job j using (jobid)
where d.start_time > now() - interval '1 day'
group by 1, 2 order by 1, 2;


-- ─── 9. Целостность: счётчик поездок совпадает с фактом? ────────────────────
select count(*) filter (where u.trips_count <> f.cnt) as расхождений,
       count(*)                                        as пользователей
from public.users u
join lateral (
  select count(*) as cnt from public.rides r
  where r.status = 'completed' and (r.creator_id = u.id or r.winner_id = u.id)
) f on true;


-- ─── 10. Что за данные сейчас живут в базе (для оценки 152-ФЗ) ──────────────
select (select count(*) from public.users)            as пользователей,
       (select count(*) from public.rides)            as поездок,
       (select count(*) from public.payments)         as платежей,
       (select count(*) from public.contact_messages) as обращений,
       (select min(created_at) from public.contact_messages) as самое_старое_обращение;


-- ─── 11. Расширения и их версии (для переезда) ──────────────────────────────
select extname, extversion, extnamespace::regnamespace as схема
from pg_extension order by 1;

-- Что загружается при старте PostgreSQL (для пункта В-4)
show shared_preload_libraries;
```
