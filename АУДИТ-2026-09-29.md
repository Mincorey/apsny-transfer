### К-2. Аноним может закрыть любой чужой аукцион и завершить любую чужую поездку

**Где.** Функции `close_auction_early` и `complete_trip`.

**В чём дело.** Это ровно та ошибка, которую 10.08 нашли и исправили в
`cancel_ride` (там даже комментарий про неё), но в двух соседних функциях
она осталась. Проверка владельца написана так:

```sql
IF v_ride.creator_id != auth.uid() THEN RAISE EXCEPTION ...
```

У анонима `auth.uid()` пустой (`NULL`). Сравнение с `NULL` даёт не «ложь», а
«неизвестно», и `IF` его пропускает — проверка молча не срабатывает.

Вторая половина: миграция `20260613_harden_03` отзывает права у `PUBLIC`,
но Supabase выдаёт права на функции роли `anon` **отдельно, напрямую**.
Отзыв у `PUBLIC` их не трогает. Итог по схеме из репозитория: `anon` может
вызвать `close_auction_early`, `complete_trip`, `place_bid`, `submit_review`,
`auto_complete_expired_rides`, `run_retention_cleanup` и две функции чистки.

**Проверено.** На собранной из миграций базе, под ролью `anon`, без входа:

```
close_auction_early(<чужая поездка>)  → {"success": true, "winner_id": ...}
complete_trip(<чужая поездка>)        → {"success": true}
```

Аукцион закрылся досрочно, победителем стал последний ставивший, поездка
завершилась, открылись контакты и возможность отзывов. Через REST это
один запрос `POST /rest/v1/rpc/close_auction_early` с публичным ключом.

**Вторая ошибка в `complete_trip` — двойной счёт поездок.** Функция сама
делает `trips_count + 1`, и триггер `trg_sync_trips_count` (с 10.08)
делает то же самое. Проверено: после одной завершённой поездки счётчик
вырос на 2. На боевой базе, судя по миграции `20260810_fix_3_2`,
`complete_trip` другая и этого не делает — но репозиторий и бой расходятся
(см. В-5), и при сборке базы из репозитория ошибка вернётся.

**На боевой базе нужно проверить** — блоки 1 и 2 файла проверки.

**Как закрыть.** Черновик исправления **проверен** на локальной базе:
аноним получает `permission denied`, чужой водитель — отказ, создатель
закрывает и завершает, счётчик растёт ровно на 1.

```sql
-- В обеих функциях первой строкой:
IF auth.uid() IS NULL THEN RAISE EXCEPTION 'Требуется авторизация'; END IF;
-- и сравнение через IS DISTINCT FROM вместо !=:
IF v_ride.creator_id IS DISTINCT FROM auth.uid() THEN ...
-- из complete_trip убрать ручное UPDATE users SET trips_count ...

revoke execute on function
  public.close_auction_early(uuid), public.complete_trip(uuid),
  public.place_bid(uuid, numeric), public.submit_review(uuid, uuid, integer, text),
  public.accept_current_price(uuid, uuid), public.cancel_ride(uuid)
from public, anon;

revoke execute on function
  public.auto_complete_expired_rides(), public.run_retention_cleanup(),
  public.cleanup_old_notifications(), public.cleanup_old_cancelled_rides()
from public, anon, authenticated;

alter function public.cleanup_old_notifications()   set search_path = public, pg_temp;
alter function public.cleanup_old_cancelled_rides() set search_path = public, pg_temp;
```

Полный текст обеих исправленных функций — в Приложении Б.

- [ ] Прогнать блоки 1–2 проверочного файла на бою
- [ ] Миграция с исправлением обеих функций и отзывом прав у `anon`
- [ ] Пройтись по **всем** функциям на шаблон `!= auth.uid()` / `<> auth.uid()` — заменить на `IS DISTINCT FROM` с проверкой входа (`delete_unpaid_draft`, `publish_ride_free`, `start_ride_payment` сейчас защищены только тем, что `anon` их не вызывает)
- [ ] Тест: аноним → `permission denied`, чужой → отказ, свой → успех и `trips_count + 1`

### К-3. Перенос базы по `MOVING_CHECKLIST.md` потеряет все права доступа

**Где.** `MOVING_CHECKLIST.md`, раздел 4:

```bash
pg_dump ... --no-owner --no-privileges --schema=public --schema=auth --schema=storage
pg_restore ... --no-owner --no-privileges
```

**В чём дело.** `--no-privileges` значит: в дамп не попадает ни один
`GRANT` и `REVOKE`. А на них держится почти вся защита проекта — полтора
десятка миграций только этим и занимались: телефоны и мессенджеры закрыты
правами на колонки, `publish_ride_paid` и `finish_auction` доступны только
серверу, `rating` и `trips_count` клиент менять не может.

На новом сервере таблицы и функции будут созданы заново, и получат права
**по умолчанию для Supabase** — а они у Supabase такие: `anon` и
`authenticated` получают всё на всё в схеме `public`. То есть сразу после
переезда:

- телефоны, Telegram, WhatsApp всех пользователей читаются без входа;
- `publish_ride_paid` может вызвать любой — публикация без оплаты;
- любой пользователь может переписать себе рейтинг и статус поездки.

Сайт при этом будет работать как обычно — заметить нельзя, пока не проверишь.

**Вторая проблема того же места.** Восстанавливать схемы `auth` и `storage`
целиком поверх свежего self-hosted Supabase нельзя: GoTrue и Storage при
первом запуске уже создают свои таблицы своих версий, и восстановление
либо упадёт на конфликтах, либо оставит структуру, не совпадающую с
версией сервиса.

**Как закрыть.**

- [ ] Переписать раздел 4 по официальной схеме Supabase: три отдельных дампа — роли, схема, данные (`supabase db dump --db-url ... --role-only`, `... -f schema.sql`, `... --data-only --use-copy`). Схема `auth` — только данные, не структура.
- [ ] Если остаётся `pg_dump` — **без** `--no-privileges`.
- [ ] После восстановления — обязательный прогон блоков 1 и 4 проверочного файла на новом сервере и сравнение с облаком. Добавить это в чеклист отдельным пунктом «переезд не завершён, пока права не совпали».
- [ ] Репетиция на тестовом сервере до дня переезда.

### В-4. Настройка PostgreSQL из `deploy/` отключит Telegram и Vault

`deploy/postgresql.tuning.conf`:

```
shared_preload_libraries = 'pg_stat_statements,pg_cron'
```

Эта строка **заменяет** список библиотек образа Supabase целиком, а не
дополняет его. В образе там ещё `pg_net`, `pgsodium`/`supabase_vault`,
`pgaudit`, `auto_explain` и другие. Без `pg_net` фоновый процесс HTTP-запросов
не стартует — `tg_notify` и уведомления о форме обратной связи перестанут
уходить. Без `pgsodium` может не расшифроваться Vault, где лежит токен бота.
В худшем случае база не поднимется, если в дампе есть расширение, требующее
предзагрузки.

То есть уведомления о **недоплате и ошибках платежей** замолчат — ровно те,
ради которых они заводились.

- [ ] Убрать строку из файла; взять значение из запущенного контейнера (`show shared_preload_libraries;`) и только **дописать** к нему, если что-то нужно
- [ ] После переезда проверить: `select net.http_post(...)` на тестовый адрес, `select count(*) from vault.decrypted_secrets`, пришло ли сообщение в Telegram

### В-5. Репозиторий не может воссоздать базу — он расходится с боем

Попытка собрать базу с нуля по инструкции `MIGRATIONS.md`
(`supabase_schema_v2.sql` + все миграции по порядку) показала:

### В-12. Безопасность самого self-hosted Supabase

### С-1. При создании поездки можно подделать служебные поля

Триггер `force_ride_draft` сбрасывает только `status`, `auction_end_time`,

```sql
new.current_price := new.start_price; new.bids_count := 0; new.last_bid_at := null;

if ((new.departure_date + new.departure_time) at time zone 'Europe/Moscow') <= now() then
  raise exception 'Время выезда уже прошло'; end if;
if new.vehicle_id is not null and not exists (select 1 from vehicles v
     where v.id = new.vehicle_id and v.driver_id = new.creator_id) then
  raise exception 'Автомобиль не принадлежит автору поездки'; end if;
```

## 8. Эквайринг Т-Бизнес: план интеграции

Серверная основа (`payments`, `start_ride_payment`, `publish_ride_paid`,
`force_ride_draft`, чистка черновиков) переиспользуется. Пишется:
инициация платежа, приёмник уведомлений, экран оплаты.

### 8.1. Схема

```
[Опубликовать] → Edge Function tbank-init (с токеном пользователя)
                   ├─ rpc start_ride_payment(ride)  → метка (OrderId)
                   ├─ POST https://securepay.tinkoff.ru/v2/Init
                   │     TerminalKey, Amount=10000 (копейки!), OrderId=метка,
                   │     Description, NotificationURL, SuccessURL, FailURL, Token
                   └─ ← PaymentURL → браузер уходит на страницу банка
Банк → POST tbank-webhook (JSON)
         ├─ проверить Token, TerminalKey, Success, Status
         ├─ Status = CONFIRMED → rpc publish_ride_paid(OrderId, PaymentId, Amount/100, raw)
         ├─ REFUNDED / REVERSED / REJECTED → записать и сообщить в Telegram
         └─ ответ: HTTP 200, тело ровно "OK" (иначе банк будет повторять)
SuccessURL → /payment?ride=…&paid=1 → опрос статуса поездки каждые 2 с, до 60 с
```

### 8.2. Что важно не ошибиться

- [ ] **Пароль терминала — только на сервере** (секрет Edge Function). В браузере его быть не должно ни в каком виде; `Init` зовётся с сервера.
- [ ] **Подпись `Token`:** берутся все параметры **верхнего уровня** (вложенные объекты `Receipt`, `DATA` — не входят), добавляется пара `Password`, всё сортируется по имени ключа, значения склеиваются в одну строку, SHA-256. Для уведомления — то же, из пришедшего JSON без самого `Token`. Булевы значения — строкой `true`/`false`.
- [ ] **Сумма в копейках.** 100 ₽ = `10000`. В `publish_ride_paid` передавать рубли (`Amount / 100`), как сейчас.
- [ ] **Проверять в уведомлении:** `TerminalKey` свой; `OrderId` известен; `Amount` не меньше ожидаемого; `Status = CONFIRMED` для одностадийной оплаты. `AUTHORIZED` — ещё не деньги.
- [ ] **Идемпотентность** уже есть в `publish_ride_paid`; `operation_id` = `PaymentId` банка.
- [ ] **Возвраты** (`REFUNDED`, `PARTIAL_REFUNDED`): статус в `payments` + сообщение в Telegram + аннулирование чека в «Мой налог» (см. 9).
- [ ] **CSP.** Переход на `PaymentURL` через `window.location` политикой `form-action` не ограничивается — достаточно убрать `https://yoomoney.ru`. Если будет виджет/iframe банка — добавить его домены в `frame-src` и `script-src`.
- [ ] **Тестовый терминал** (`…DEMO`) и прогон тест-кейсов банка до боевого.
- [ ] **Тексты:** `PAYMENT_PROVIDER` → «Т-Банк»; оферта, политика, условия, страница платных услуг; `ОПИСАНИЕ-ДЛЯ-МОДЕРАЦИИ-ЮMoney.md` → под анкету Т-Бизнес.
- [ ] **Порядок включения** (исправленный В-8): задеплоить обе функции → проверить на тестовом терминале → боевой терминал → платёж 100 ₽ самому себе → и только потом одной выкладкой: новый интерфейс + `payments-enable.sql`.

Детали протокола сверять по официальной документации:
[инициализация платежа](https://developer.tbank.ru/eacq/api/init),
[уведомления](https://www.tinkoff.ru/kassa/develop/api/notifications/),

Прочитать страницы документации напрямую из этой сессии не удалось

## 9. ИП на НПД и приём оплаты

Вы — ИП, применяющий налог на профессиональный доход. Это законная и
распространённая схема, и она влияет на три вещи в проекте.

**Реквизиты.** Сейчас в `siteInfo.ts` статус «самозанятый, плательщик НПД» и
только ИНН. Для ИП в оферте и на странице оплаты указываются: ФИО полностью
с пометкой «ИП», ОГРНИП, ИНН, налоговый режим (НПД), контактный email.
Банк при подключении эквайринга сверяет реквизиты на сайте с документами.

- [ ] Поле `ogrnip` в `OPERATOR`, статус «Индивидуальный предприниматель, применяющий НПД»; вывести в оферте, условиях, на `/payment` и в квитанции

**Чеки.** На НПД онлайн-касса (54-ФЗ) не нужна; чек формируется в
«Мой налог». При безналичной оплате его можно сформировать не сразу, а до
9-го числа следующего месяца, но на **каждый** платёж. При возврате чек
аннулируется. Т-Бизнес для ИП на НПД умеет регистрировать доход сам —
это стоит включить, иначе на каждые 100 ₽ придётся заходить в приложение.
Объект `Receipt` в `Init` при этом, скорее всего, не передаётся — он для
онлайн-кассы. **Уточнить у менеджера Т-Бизнес при подключении.**

- [ ] Уточнить у банка автоматическую регистрацию дохода НПД и нужен ли `Receipt`
- [ ] В оферте раздел 3 уже написан под НПД — поправить только название банка

**Ограничения режима.**

- Лимит дохода — 2,4 млн ₽ в год. При 100 ₽ за публикацию это 24 000 публикаций; до лимита далеко, но за ним нужно следить.
- **На НПД нельзя быть посредником** по договорам поручения, комиссии и агентским. Сейчас сервис продаёт **свою** услугу — публикацию, — а за поездку люди рассчитываются между собой напрямую. Это правильно, и так должно остаться: принимать оплату самой поездки через сайт (даже «для удобства», даже как депозит) на НПД нельзя.
- Нельзя нанимать сотрудников по трудовому договору.

Я не юрист и не налоговый консультант. Выше — общие правила, которые стоит
подтвердить у Т-Бизнес при подаче заявки и у бухгалтера.

## Приложение Б. Черновик исправления К-2 (проверен на локальной базе)

Не применён никуда. Перед применением — сверить с текстом функций на бою
(блок 2 проверочного файла): если боевая `complete_trip` отличается, брать
за основу её.

```sql
create or replace function public.close_auction_early(p_ride_id uuid) returns jsonb language plpgsql security definer set search_path = public, pg_temp as $$
declare v_ride record; v_winner_id uuid; v_uid uuid := auth.uid();
begin
  if v_uid is null then raise exception 'Требуется авторизация'; end if;
  select * into v_ride from public.rides where id = p_ride_id for update;
  if not found then raise exception 'Поездка не найдена'; end if;
  if v_ride.creator_id is distinct from v_uid then raise exception 'Только создатель поездки может закрыть аукцион'; end if;
  if v_ride.status <> 'active' then raise exception 'Аукцион уже завершён'; end if;
  select bidder_id into v_winner_id from public.bids where ride_id = p_ride_id order by created_at desc limit 1;
  if v_winner_id is null then raise exception 'Нет ставок для завершения аукциона'; end if;
  update public.rides set status='booked', winner_id=v_winner_id, auction_end_time=now() where id=p_ride_id;
  insert into public.notifications (user_id,type,title,body,ride_id) values (v_winner_id,'auction_won','Вы выиграли аукцион!','Поздравляем! Поездка '||v_ride.origin||' → '||v_ride.destination||' ваша.',p_ride_id);
  insert into public.notifications (user_id,type,title,body,ride_id) select distinct b.bidder_id,'auction_lost','Аукцион завершён','По поездке '||v_ride.origin||' → '||v_ride.destination||' выбрали другого участника.',p_ride_id from public.bids b where b.ride_id=p_ride_id and b.bidder_id<>v_winner_id;
  return jsonb_build_object('success',true,'winner_id',v_winner_id);
end $$;
create or replace function public.complete_trip(p_ride_id uuid) returns jsonb language plpgsql security definer set search_path = public, pg_temp as $$
declare v_ride record; v_uid uuid := auth.uid();
begin
  if v_uid is null then raise exception 'Требуется авторизация'; end if;
  select * into v_ride from public.rides where id = p_ride_id for update;
  if not found then raise exception 'Поездка не найдена'; end if;
  if v_ride.creator_id is distinct from v_uid then raise exception 'Только создатель поездки может завершить её'; end if;
  if v_ride.status <> 'booked' then raise exception 'Поездка должна быть в статусе booked для завершения'; end if;
  update public.rides set status='completed' where id=p_ride_id;  -- trips_count считает триггер trg_sync_trips_count
  return jsonb_build_object('success',true);
end $$;
```
