## 3. ✅ P1 — Приватность контактов — ЗАКРЫТО 2026-06-13

> **Сделано.** На уровне БД отозван табличный `SELECT` на `public.users` у `anon`/`authenticated` и выдан заново только на не-PII колонки (`id, full_name, role, avatar_url, rating, trips_count, created_at, show_*`). Контактные колонки (`email, phone, telegram, whatsapp, max`) теперь **физически недоступны** для прямого чтения с клиента. Доступ к ним — только через SECURITY DEFINER функции, которые серверно проверяют права:
> - `get_my_profile()` — свой профиль целиком (для редактирования);
> - `get_user_profile(uuid)` — чужой профиль: контакты только при own / совместной завершённой поездке / включённом `show_*`-флаге;
> - `get_trip_view(uuid)` — обновлена: creator-контакты отдаются только победителю/создателю после `booked/completed` (с учётом каждого `show_*`), winner-контакты — только создателю.
>
> Фронтенд переведён на эти RPC: `Profile.tsx` (`get_my_profile`), `UserProfile.tsx` (`get_user_profile`), `TripDetail.tsx` (`get_trip_view` — заодно минус несколько запросов на самой горячей странице).
>
> **Протестировано на проде** (симуляция ролей через `request.jwt.claims`): аноним — контакты `null`; победитель видит телефон создателя; создатель видит телефон победителя; совместная поездка открывает контакты в профиле; прямое чтение `phone`/`email` ролью `authenticated` → `insufficient_privilege`. Публичные колонки (имя/аватар/рейтинг) читаются как прежде.
>
> Миграция: `supabase/migrations/20260613_p1_contact_privacy.sql`.
> ⚠️ Финальную проверку типов/сборки (`npx tsc --noEmit && npm run build`) прогнать локально — в песочнице была рассинхронизация ФС, поэтому tsc там недостоверен; сами файлы проверены чтением и корректны.

### 3-исходное. 🔴 P1 — Приватность контактов (описание проблемы)

**Суть:** контакты (`phone`, `telegram`, `whatsapp`) скрываются только в интерфейсе, а на уровне БД таблица `users` читается политикой `SELECT USING (true)`. Значит **любой пользователь — и даже неавторизованный — может прямым REST-запросом `select phone,telegram,whatsapp from users` вытащить контакты всех**. Это напрямую противоречит главному правилу сервиса «контакты открываются только победителю после аукциона».

Усугубляют:
- `UserProfile.tsx` делает `select('*')` по чужому профилю → тянет все контакты на клиент (и egress, и PII), а показывает по флагу `show_*` — гейт чисто клиентский.
- `TripDetail.tsx` джойнит контактные колонки напрямую; ограничение «только участникам» — тоже клиентское.

**План фикса (БД + фронт вместе):**
1. Перевести чтение поездки на уже существующую RPC **`get_trip_view`** — она отдаёт контакты только авторизованному и по факту отношения (создатель/победитель), серверно.
2. Для чужого профиля — отдавать контакты только при наличии завершённой совместной поездки (логика уже есть в `UserProfile` для блока отзывов — переиспользовать через RPC).
3. На уровне БД закрыть прямое чтение PII-колонок: `REVOKE SELECT (phone, telegram, whatsapp) ON public.users FROM anon, authenticated;` (PostgREST уважает колоночные привилегии), оставив их доступными только внутри `SECURITY DEFINER` RPC.
4. Убрать `select('*')` в `UserProfile` → явные безопасные колонки.

Это и приватность, и заодно минус трафик/round-trips на самой горячей странице.

## 4. 🟡 Важное (до публичного запуска желательно)

### ✅ R1 — Отзыв «пассажир → водитель» — ЗАКРЫТО 2026-06-13
Раньше отзыв жёстко шёл «победитель → создатель»: для `request` это давало «водитель оценивает пассажира». Переделано на правило **пассажир оценивает водителя** независимо от типа (роли выводятся из `type`: `offer` — водитель=создатель, пассажир=победитель; `request` — наоборот).
- БД: `submit_review` теперь требует `reviewer = пассажир`, `target = водитель`; `get_trip_view.has_reviewed` считается по пассажиру. Миграция `supabase/migrations/20260613_r1_reviews_passenger_rates_driver.sql`.
- Фронт (`TripDetail.tsx`): добавлены роли `driverId/passengerId/isPassenger`; `reviewTarget` = водитель; `canLeaveReview` = `isCompleted && isPassenger && !hasReviewed`; подписи приведены к роли (в т.ч. «Свяжитесь с пассажиром/водителем» в блоке победителя).
- Протестировано на проде по 4 кейсам (offer/request × пассажир/водитель): пассажир оценивает водителя в обоих типах, водитель оценить не может. Тестовые вставки откатаны.

### I7 — Отзывы односторонние — РЕШЕНО ПРОДУКТОВО (двусторонние не нужны)
По решению: оцениваются только водители, рейтинг пассажиров не вводим («доверенные водители» полезнее). Текущая односторонняя модель (пассажир → водитель) — целевая. Закрывается пунктом R1.

### I8 — Правка/удаление отзыва — РЕШЕНО НЕ ДЕЛАТЬ
По решению: возможность править/удалять отзыв не нужна (нет сценария, где это требуется). Оставляем отзывы неизменяемыми.

## 6. ⚙️ Оптимизации БД/трафика для Free-тарифа

REST безлимитен по числу, но тратит egress (5 ГБ/мес) и shared-CPU. Дополнительно к уже сделанному:

1. **Перевести `TripDetail` на `get_trip_view`** — вместо 3–4 обращений (поездка + ставки + проверка отзыва + ленивое закрытие) один RPC одним JSON. Меньше round-trips и egress на самой посещаемой странице. (Совмещается с фиксом P1.)
2. **`UserProfile`/`Profile`: убрать `select('*')`** → явные колонки. Меньше egress, не тянем PII.
3. **Кэш-заголовки на бакете `avatars`** (долгий `cache-control`) — повторные просмотры аватаров не тратят egress.
4. **Пагинация ленты** вместо `limit(50)` одним куском — подгрузка по скроллу (когда поездок станет много).
5. **Счётчик непрочитанных** можно считать по таблице `notifications` (тип `new_message`) вместо скана `messages` — но текущий вариант на опросе тоже приемлем.
6. **«Грелка» от авто-паузы Free** (проект засыпает после 7 дней простоя): внешний пингер раз в несколько часов на лёгкий health-endpoint. На старте, пока трафик тихий, актуально.

Состояние БД в целом: **здоровое**. Единственный оставшийся пункт уровня БД — колоночные привилегии на PII (раздел 3).

## 7. 🧪 Смоделированные сценарии (end-to-end)

**Пассажир (запрос «Я еду»):** регистрация (role=passenger) → триггер `handle_new_user` создаёт профиль → создание поездки `type=request, status=active` → водители снижают цену (`place_bid`) → создатель закрывает досрочно (`close_auction_early`) либо таймер/ленивое закрытие (`finish_auction`) → `booked`, `winner_id`=водитель, проигравшим уходит `auction_lost` → **контакты открываются создателю и победителю** → создатель жмёт «Завершить» (`complete_trip`) → `completed`, `trips_count +1` обоим → отзыв (см. R1: подпись «водитель» некорректна для этого направления).

**Водитель (предложение «Я везу»):** регистрация (role=driver, профиль без авто — авто добавляется позже в Profile) → создание `type=offer` (авто необязательно — см. I4 в старом аудите) → пассажиры повышают ставку → закрытие/таймер → `booked`, победитель-пассажир → контакты открываются взаимно → завершение → отзыв победителя о создателе («оценить водителя» — здесь корректно).

**Разрывы, найденные при моделировании:** приватность контактов (P1), односторонние отзывы (I7) и неверная подпись отзыва для запросов (R1). Остальная цепочка консистентна.
