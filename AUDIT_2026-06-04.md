## 2. Архитектура

**Стек:** React 19 + Vite 6 + React Router 7 (BrowserRouter) + Tailwind 4 + Supabase (Postgres + Auth + Realtime + Storage). Бэкенд отдельный не пишется — вся логика в Postgres через `SECURITY DEFINER` RPC-функции. Motion для анимаций, lucide для иконок. PWA-манифест присутствует.

**Таблицы:** `users`, `vehicles`, `rides`, `bids`, `conversations`, `direct_messages`, `messages` (групповой чат поездки), `reviews`, `notifications`.

**RPC:** `place_bid`, `accept_current_price`, `close_auction_early`, `complete_trip`, `cancel_ride`, `finish_auction`, `submit_review`, `get_or_create_conversation`, `process_expired_auctions`, `auto_complete_expired_rides`.

**Жизненный цикл поездки:** `active` → (ставки) → `booked` (победитель выбран) → `completed` (водитель/cron подтвердил) либо `cancelled`.

## 3. Смоделированные сценарии (от регистрации до завершения)

### 3.1 Пассажир («Я еду»)

1. Регистрация: `signUp` (роль `passenger`) → `upsert` в `users`. → ⚠️ см. **I1** (зависит от настройки подтверждения email).
2. Создаёт поездку → `rides.insert` с `type='request'`, `status='active'`, задаёт стартовую цену, шаг и длительность аукциона. `auction_end_time` = now + N часов.
3. Водители делают ставки **на понижение** (`place_bid`, проверка шага и направления). Пассажир получает realtime-toast о каждой ставке.
4. Пассажир либо ждёт таймер, либо закрывает аукцион досрочно (`close_auction_early`) → поездка `booked`, выбран `winner_id` (водитель).
5. После поездки **создатель** (пассажир) жмёт «Завершить» (`complete_trip`) → `completed`, `trips_count +1` обоим.
6. Отзыв оставляет **победитель** (водитель) о создателе (`submit_review`). → ⚠️ обратного отзыва нет, см. **I7**.

### 3.2 Водитель («Я везу»)

1. Регистрация (роль `driver`) → профиль создан, **но без автомобиля**. → ⚠️ см. **I4**.
2. Авто добавляется только позже в Profile (`vehicles.insert`).
3. Создаёт предложение → `type='offer'`, `status='active'`. `vehicle_id` **необязателен** — offer можно создать без машины.
4. Пассажиры делают ставки **на повышение** (выкупают места дороже).
5. Закрытие аукциона/таймер → `booked`, победитель — пассажир.
6. Водитель (создатель) жмёт «Завершить» → `completed`. Победитель-пассажир оставляет отзыв.

### 3.3 Что в цепочке проседает

- Регистрация→профиль держится только на клиентском upsert (хрупко при email-подтверждении) — **I1**.
- Проигравшие ставщики **не уведомляются** — тип `auction_lost` объявлен, но никогда не создаётся — **I6**.
- Отзывы односторонние — **I7**.
- Роль фиксируется навсегда; «и вожу, и езжу» невозможно — **I3**.

**Фикс:** добавить в корень `vercel.json`:
```json

```

### 🔴 B2 — Проект не под git 🔲
`.git` отсутствует — переносить на GitHub нечего. Перед первым коммитом убедиться, что `.gitignore` исключает `.env` (он исключает, оставляя только `.env.example` — ок).
**Фикс:** `git init && git add . && git commit -m "initial"`.

### 🔴 B3 — Service-ключ Supabase во фронтовом `.env` 🔲
`.env` содержит `VITE_SUPABASE_SERVICE_KEY`. В текущий бандл он **не попал** (нигде не используется), но префикс `VITE_` означает, что при любой случайной ссылке Vite **вшьёт его в публичный JS** — это полный обход RLS. Service-ключ во фронт-проекте быть не должен в принципе.
**Фикс:** удалить `VITE_SUPABASE_SERVICE_KEY` из `.env` и `.env.example`; если он нужен серверным задачам — хранить только в серверной среде (Supabase secrets / отдельный backend), никогда с префиксом `VITE_`. Заодно убрать неиспользуемые `GEMINI_API_KEY` и `APP_URL` из `.env.example` (артефакты AI Studio).

### ✅ I1 — Создание профиля надёжно (триггер handle_new_user) — ЗАКРЫТО 2026-06-05
> Триггер `handle_new_user` на `auth.users` **применён к боевой БД и проверен** (функция есть, триггер активен, `anon` не может вызывать, `search_path` закреплён). **Фикс (рекомендуется):** перенести создание профиля в БД-триггер `handle_new_user` на `auth.users` (AFTER INSERT, SECURITY DEFINER) — это надёжно при любой настройке. Триггера сейчас в миграциях **нет**.

## 7.1 Нагрузочная модель — 500 одновременных пользователей (добавлено 2026-06-04)

**Сценарий:** ~500 онлайн в пик сезона (≈200 водителей + 300 пассажиров), смесь «мониторят ленту», «смотрят страницу аукциона», «создают поездки», «торгуются», «переписываются».

**Слой 1 — Vercel (статика).** Это SPA: на Vercel отдаётся собранный `dist` (JS gzip ~225 КБ + CSS ~13 КБ) с CDN-эджей. 500 (и даже 50 000) пользователей для статики с кэшем — **не нагрузка**. Vercel узким местом не является. Нюанс не про ёмкость, а про лицензию: коммерческий сервис требует план Vercel Pro (Hobby — для некоммерческого).

**Слой 2 — Postgres / PostgREST (REST-запросы).** Фронт ходит через PostgREST → пул Supavisor → Postgres, поэтому **500 пользователей ≠ 500 коннектов к БД** — PostgREST мультиплексирует. Запросы простые и индексированные (лента: 1 select limit 50 + join; бейдж: 2 select + count; уведомления: 1). Грубо ~5–15 запросов/мин на юзера → ~80 запросов/сек на платформу — это **легко** даже для small-compute. Подтверждено: посекундных опросов БД нет (таймеры — клиентские). Контеншн по «горячей» строке аукциона (`SELECT ... FOR UPDATE` на одной `rides`) сериализует ставки по этой поездке — это корректно и в пределах человеческого темпа торгов. **Вывод: реляционный слой 500 онлайн держит спокойно** — при условии, что индексы из B4 реально применены в проде.

**Слой 3 — Realtime (узкое место).**
- **Конкурентные подключения:** каждый залогиненный = 1 WebSocket (каналы мультиплексируются) → ~500 одновременных realtime-коннектов. Free-тариф = лимит **200** (упрётся уже на 200 юзерах). Pro = **500 по умолчанию** — ровно по потолку, нужен запрос на увеличение в поддержку Supabase.
- **Веерная рассылка (главная проблема архитектуры):**
  - `Feed.tsx` подписан на `event:'*'` по **всей** таблице `rides` **без серверного фильтра** → каждое изменение любой поездки рассылается каждому, кто смотрит ленту.
  - `useUnreadCount` подписан на **все** INSERT/UPDATE в `messages` без фильтра и на **каждое** событие выполняет `COUNT`-запрос.
  - Пример: одна ставка = 1 UPDATE `rides` + 1 INSERT `bids`. UPDATE веерно уходит, скажем, 300 смотрящим ленту = **300 realtime-сообщений на одну ставку**. При скромной 1 ставке/сек по платформе → ~18 000 сообщений/мин ≈ десятки млн/день. Pro включает 5 млн сообщений/мес → **квота выгорает за часы пика**, дальше — оплата сверх.
  - Один чат-месседж → рассылка всем 500 подписчикам бейджа → каждый запускает `COUNT` → **+500 ненужных запросов к БД на одно сообщение**.
- **Вывод:** realtime при 500 *работает*, но **неэффективен by design** — безфильтровые подписки на целые таблицы превращают одно событие в сотни сообщений и запросов. Стоимость и лаги клиентов растут сверхлинейно — ровно в тот момент (горячие аукционы в сезон), ради которого делается сервис.
