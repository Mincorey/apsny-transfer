## 0. Главный принцип (от него зависит всё остальное)

Точные лимиты **Supabase Free** (проверено на июнь 2026):

| Ресурс | Лимит Free | Дефицитный? |
|---|---|---|
| **Realtime — пик одновременных подключений** | **200** | 🔴 ДА — главный потолок |
| **Realtime — сообщений в месяц** | **2 млн** | 🟡 да, при веерных рассылках |
| REST/API запросы | **безлимит** | 🟢 нет |
| БД (Postgres) | 500 МБ, shared CPU | 🟡 следить за ростом |
| Файлы (Storage) | 1 ГБ | 🟡 аватары/фото авто |
| Egress (исходящий трафик БД+Storage) | 5 ГБ/мес | 🟡 да |
| MAU (авторизации) | 50 000 | 🟢 нет |
| Edge Functions | 500 000 вызовов/мес | 🟢 нет — хватит на webhook |
| Авто-пауза проекта | через 7 дней простоя | 🟡 учесть |
| Бэкапы | ❌ нет | 🔴 риск для платного сервиса |

**Вывод-стратегия:** обычные запросы (REST) бесплатны и безлимитны — их можно делать сколько угодно. Платим (упираемся в лимит) за **постоянные realtime-сокеты** и **веерные realtime-сообщения**. Поэтому вся оптимизация сводится к одной идее:

> 🎯 **Убрать «всегда включённые» realtime-подписки и веерные рассылки, заменив их на дешёвые REST-запросы (опрос по таймеру / при фокусе вкладки / по требованию). Realtime оставить точечно — только там, где живое обновление реально нужно (открытая страница активного аукциона, открытый чат).**

После этого «500 пользователей» перестают означать «500 сокетов»: сокет держат только те, кто прямо сейчас смотрит живой аукцион или открытый чат — это десятки, а не сотни. Free-тариф становится реальным для запуска.

## 1. Realtime — разбор каждой подписки и варианты (САМОЕ ВАЖНОЕ)

Сейчас в коде 8 мест с `postgres_changes`. Делю на «убрать/заменить» и «оставить точечно».

### 1.1 ✅ `useUnreadCount.ts` — подписка на ВСЮ таблицу `messages` (худший случай) — СДЕЛАНО 2026-06-04 (Вариант A)
> Реализован Вариант A: realtime убран полностью, счётчик считается опросом раз в 30 сек (+ пауза опроса при скрытой вкладке, мгновенное обновление при возврате). tsc и сборка зелёные.
**Проблема:** каждый залогиненный пользователь подписан на все INSERT/UPDATE в `messages` **без фильтра**, и на каждое событие выполняет `COUNT`-запрос. Одно сообщение в любом чате → событие всем онлайн → у каждого летит COUNT. Это и постоянный сокет, и веерная рассылка, и амплификация запросов разом.

**Варианты (от простого к лучшему):**
- **Вариант A (рекомендую для Free):** убрать realtime полностью, считать непрочитанные **опросом раз в 30–60 сек** (`setInterval` → один `COUNT`-запрос). REST безлимитен; задержка появления бейджа до минуты некритична.
- **Вариант B:** считать непрочитанные через таблицу `notifications` (там уже есть тип `new_message` и фильтр по `user_id`), а не сканировать `messages`. Тогда бейдж берётся из той же подписки, что и тосты (см. 1.2) — ноль дополнительных сокетов.
- **Вариант C:** обновлять счётчик только при заходе на вкладку (Page Visibility API: `visibilitychange` → один COUNT). Нет таймера вообще.
- **Вариант D (минимальная правка):** оставить realtime, но добавить серверный фильтр и дебаунс — слабее A/B, не убирает сокет.

### 1.2 ✅ `MainLayout.tsx` — подписка на свои `notifications` — СДЕЛАНО 2026-06-04 (Вариант A)
> Реализован Вариант A: realtime убран, новые уведомления опрашиваются раз в 20 сек REST-запросом с дедупликацией по `created_at > since` (since = момент загрузки страницы), тосты для новых; пауза при скрытой вкладке + догон при возврате. tsc и сборка зелёные.
**Проблема:** фан-аута нет (фильтр корректный), но это **постоянный сокет на каждого онлайн-пользователя** весь сеанс → прямой удар по лимиту 200 одновременных.

**Варианты:**
- **Вариант A (рекомендую):** опрашивать новые уведомления раз в 20–30 сек REST-запросом (`SELECT ... WHERE is_read=false ORDER BY created_at DESC`), показывать тосты для новых. Сокет не нужен → лимит 200 больше не привязан к «числу онлайн».
- **Вариант B (гибрид, лучший UX/нагрузка):** держать realtime-сокет **только когда вкладка видима** (`visibilitychange`: при скрытии — `removeChannel`, при возврате — переподписка + один догоняющий запрос). Скрытые вкладки (а их всегда много) перестают занимать слоты из 200.
- **Вариант C:** подписку на уведомления держать только на «тяжёлых» страницах (например, TripDetail активного аукциона), а в остальное время — опрос.

### 1.3 ✅ `Feed.tsx` — подписка на ВСЮ таблицу `rides` — СДЕЛАНО 2026-06-04 (Вариант A)
> Реализован Вариант A: realtime убран, лента обновляется опросом раз в 15 сек + при возврате на вкладку + кнопка «Обновить» (добавлена — в коде её не было). Список заменяется целиком (booked/completed корректно исчезают). tsc и сборка зелёные.
**Проблема:** каждое изменение любой поездки рассылается всем, кто смотрит ленту → веер + сокет у каждого зрителя ленты.

**Варианты:**
- **Вариант A (рекомендую):** убрать realtime из ленты, обновлять список **по таймеру раз в 15–30 сек** + **при фокусе вкладки** + кнопка «Обновить» (она уже есть). Для ленты свежесть в 15–30 сек достаточна; живая цена важна на странице самой поездки, а не в ленте.
- **Вариант B:** оставить realtime, но добавить серверный фильтр `status=eq.active` (рассылаются только активные) —半 меры, сокет остаётся.
- **Вариант C:** «мягкий live» — подписка только на INSERT новых поездок (показывать «↑ N новых поездок, нажмите чтобы обновить»), без потока UPDATE по ценам.

### 1.4 🟢 `TripDetail.tsx` — каналы `trip-${id}` и `trip-bids-${id}` (ОСТАВИТЬ)
Здесь живое обновление **оправдано**: пользователь смотрит конкретный активный аукцион, цена меняется в реальном времени.
**Доработки:** (1) подписываться только если `status='active'` (для booked/completed/cancelled realtime не нужен); (2) убедиться, что каналы фильтруют по `id`/`ride_id=eq.<id>` (точечно, без веера); (3) канал закрывается при уходе со страницы (уже реализовано через cleanup). Итог: сокеты держат только зрители живых аукционов — небольшое подмножество.

### 1.5 ✅ Чаты: `Chat`, `Messages`, `Conversations`, `DirectChat` — СДЕЛАНО 2026-06-04
> Realtime убран со списков `Messages` и `Conversations` (обновление при заходе + при фокусе/возврате на вкладку). Realtime сохранён внутри открытых диалогов `Chat` и `DirectChat`. tsc и сборка зелёные.
- **Оставить realtime внутри открытого диалога** (`Chat`, `DirectChat`) — это нужный live.
- **Убрать realtime со списков** (`Messages`, `Conversations`) → обновлять при заходе на страницу и при фокусе. Списки не требуют мгновенности.

### Итог по разделу 1
После правок типичный путь «зашёл → смотрит ленту → открывает поездки» держит **0 постоянных сокетов** (всё на опросе). Сокет открывается только на странице активного аукциона или в открытом чате и закрывается при уходе. **Пик одновременных подключений падает с «≈все онлайн» до «те, кто сейчас внутри живого аукциона/чата»** — это реально удержать под 200 даже при тысячах зарегистрированных.

## 2. Сокращение и удешевление REST-запросов

REST безлимитен по числу, но каждый ответ тратит **egress (5 ГБ/мес)**, грузит **shared CPU** и мобильный трафик пользователей (важно для Абхазии). Поэтому ужимаем.

1. ✅ **СДЕЛАНО 2026-06-04 (Feed).** Заменить `select('*')` на список нужных колонок. `Feed.tsx` теперь запрашивает только поля интерфейса `FeedRide` (минус `creator_id`/`winner_id`/`vehicle_id`). `Profile.tsx` — пока на `*` (одна строка своего профиля, эффект незначителен; можно сделать позже). Каст приведён к `as unknown as FeedRide[]` (строгая типизация встроенной связи).
2. ✅ **СДЕЛАНО 2026-06-04 (Auth, вариант «c»).** Лендинг кэширует 4 агрегатных запроса статистики в localStorage (TTL 1 час): мгновенный показ из кэша + фоновое обновление по сети только при отсутствии/устаревании кэша. При ошибке обновления старые значения не сбрасываются. Варианты (a) таблица `stats` + `pg_cron` и (b) одна RPC остаются как дальнейшее улучшение, если анонимного трафика станет много.
3. **`useUnreadCount` делает 2 запроса (`rides.id` + `bids.ride_id`) на каждый монтаж** — кэшировать список `ride_id` в памяти/сессии, не пересобирать постоянно.
4. **Профильные лидерборды** (2×50 строк водителей/пассажиров) грузятся при каждом открытии `Profile` — вынести только на страницу `Ratings` или кэшировать.
5. **Объединять связанные запросы в одну RPC.** `TripDetail` при открытии делает несколько обращений (поездка + ставки + проверка отзыва + проверка совершённой поездки). Одна RPC `get_trip_view(p_ride_id)` вернёт всё одним JSON → меньше round-trip и egress.
6. **Пагинация/бесконечная лента** вместо `limit(50)` одним куском; подгружать по мере прокрутки.
7. **Дебаунс** любых refetch, вызванных событиями (не чаще раза в N секунд).

## 5. Авто-пауза Free и автозавершение аукционов

- Free **ставит проект на паузу после 7 дней простоя**. При живом трафике это не наступит; на старте (пока тихо) — может. Решение: «грелка» — Vercel Cron или внешний аптайм-пингер раз в несколько часов дёргает лёгкий health-endpoint.
- Пауза также останавливает `pg_cron`. Поэтому **хорошо, что в `TripDetail` уже есть «ленивое» закрытие аукциона** (при открытии истёкшего аукциона вызывается `finish_auction`). На Free это и оставить основным механизмом; `pg_cron`/Edge Function — как резерв. Истёкшие аукционы закрываются, когда их кто-то открывает.

## 6. Интеграция AnyPay — платная публикация поездки

### 6.1 Тарифы AnyPay (на июнь 2026)
Безналичный расчёт **от 3%**, электронные деньги **от 2%**, мобильные платежи **от 3.5%**, наличные **от 5%**. Индивидуальные тарифы при обороте > $10 000/мес. AnyPay заявляет поддержку компаний, ИП **и физлиц/самозанятых**.

### 6.2 ⚠️ Важная оговорка (не юридическая консультация)
Систематический приём дохода **как физлицо без статуса** (ИП/самозанятость) в РФ несёт налоговые и юридические последствия. Самый лёгкий легальный путь — **самозанятость (НПД)**, и AnyPay её поддерживает. Также AnyPay проводит **модерацию сайта**: понадобятся реальный домен, **публичная оферта**, контакты, описание услуги, политика возврата. Рекомендую заложить эти страницы и проконсультироваться по налогам до подключения. Я не юрист — это флаг, а не совет.

### 6.3 Архитектура оплаты (серверно-доверенная, без утечки ключей)
Никогда не доверять клиенту отметку «оплачено» — только подписанный webhook от AnyPay на сервере.

**Новый жизненный цикл поездки:** добавить статус `pending_payment` (или `draft`).
1. `CreateTrip` создаёт поездку со статусом **`pending_payment`** (в ленте не видна — лента и так фильтрует `status='active'`).
2. Фронт перенаправляет на платёжную страницу AnyPay (SCI) с параметрами: `merchant_id`, `pay_id = ride_id`, `amount = фикс. плата`, `currency`, `desc`, `sign` (подпись), `success_url`, `fail_url`. Точную строку для `sign` (обычно `md5(currency:amount:secret:merchant_id:pay_id)`) сверить в личном кабинете AnyPay → раздел «Разработчикам/SCI».
3. AnyPay при успехе вызывает ваш **`notify_url` (webhook)**. Реализовать его как **Supabase Edge Function** (500k вызовов/мес бесплатно). Функция: проверяет подпись по секрету (секрет — в **Supabase secrets**, не во фронте), находит поездку по `pay_id`, ставит `status='active'`, пишет строку в `payments`, **возвращает `OK`** (AnyPay повторяет до получения OK).
4. `success_url` возвращает пользователя в приложение (например, на страницу поездки / `/my-trips`).

**Новая таблица `payments`:**
```sql
CREATE TABLE public.payments (
  id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  ride_id         UUID REFERENCES public.rides(id) ON DELETE SET NULL,
  user_id         UUID NOT NULL REFERENCES public.users(id) ON DELETE CASCADE,
  amount          NUMERIC(10,2) NOT NULL,
  currency        TEXT NOT NULL DEFAULT 'RUB',
  status          TEXT NOT NULL DEFAULT 'pending'
                    CHECK (status IN ('pending','paid','failed','refunded')),
  provider        TEXT NOT NULL DEFAULT 'anypay',
  provider_txn_id TEXT,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  paid_at         TIMESTAMPTZ
);
ALTER TABLE public.payments ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Свои платежи видны" ON public.payments FOR SELECT USING (auth.uid() = user_id);
-- INSERT/UPDATE только из Edge Function (service role) — обычным клиентам запрещено
```
Edge Function — единственное место, где живёт service-ключ (увязывается с замечанием **B3** аудита: убрать service-ключ из фронтового `.env`).

### 6.4 Варианты модели монетизации (на выбор)
- **A. Фикс за публикацию (что планируете):** просто и предсказуемо. Минус — платят даже если поездка не «выстрелила». Стоит продумать **возврат** (статус `refunded`), если на поездку не было ставок/она отменена.
- **B. Бесплатная публикация + комиссия за успешную сделку:** платит победитель/создатель при завершении. Лучше согласует интересы (платят за результат), но сложнее технически и нужен момент удержания.
- **C. Подписка для водителей** (например, помесячно «безлимит публикаций»): удобно частым перевозчикам, ровный доход вам.
- **D. Гибрид:** первые N публикаций в месяц бесплатно, далее — фикс; или фикс + платное «поднятие» поездки в ленте.

Технически проще всего стартовать с **A**, заложив таблицу `payments` так, чтобы B/C/D добавлялись без переделки.

## 8. Честный вывод по Free-тарифу

После Этапа 1 Free-тариф **реально выдержит запуск и первые сотни одновременных пользователей**: постоянные сокеты исчезают, веерные рассылки убраны, REST безлимитен. Узкими местами по мере роста станут по порядку: (1) пик realtime-подключений к живым аукционам — но это уже сотни *активных торгующихся*, а не всех онлайн; (2) egress 5 ГБ; (3) 500 МБ БД.

**Но:** для сервиса, через который идут **деньги**, главный аргумент за Pro ($25/мес) — **отсутствие бэкапов и SLA на Free**. Рекомендация: **запускаться и проверять спрос на Free** с оптимизациями из Этапов 1–3, а **до выхода на заметные платежи перейти на Pro** ради бэкапов и запаса по подключениям. Сделанные оптимизации не пропадут — они и на Pro снижают счёт и улучшают отзывчивость.
