### 1.2 RLS-политики

**Существующие политики:**

| Таблица | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| users | Все (true) | auth.uid() = id | auth.uid() = id | — |
| vehicles | Все (true) | driver_id = uid | driver_id = uid | driver_id = uid |
| rides | Все (true) | creator_id = uid | creator_id = uid | — |
| bids | Все (true) | bidder_id = uid | — | — |
| conversations | user1/user2 = uid | user1/user2 = uid | user1/user2 = uid | — |
| direct_messages | через JOIN conversations | sender_id = uid | через JOIN conversations | — |
| reviews | Все (true) | reviewer_id = uid | — | — |
| notifications | user_id = uid | true (!) | — | — |

**Критические проблемы RLS:**

1. **Уведомления: политика INSERT `WITH CHECK (true)`** — любой аутентифицированный пользователь может создать уведомление для любого другого пользователя. Это должно работать только через SECURITY DEFINER функции, но политика это не принуждает.

2. ✅ **~~Телефоны видны всем без аутентификации.~~** ~~Поля `phone`, `telegram`, `whatsapp`, `max` возвращаются политикой `SELECT USING (true)` даже для анонимных пользователей. Настройки `show_phone`, `show_telegram` и т.д. проверяются только на фронтенде — их легко обойти прямым запросом к API.~~ → Исправлено: `REVOKE SELECT (phone, telegram, whatsapp, max, email) ON public.users FROM anon` — анонимный role больше не может читать контактные поля. `TripDetail.tsx` обновлён: не запрашивает контакты для неавторизованных. Миграция `20260522_fix_users_anon_access.sql`.

3. **Ставки видны всем без аутентификации** (`SELECT USING (true)`) — это намеренное решение, но в сочетании с открытыми контактами создаёт риск сбора данных.

4. **Отзывы: нет политики UPDATE/DELETE** — отзыв нельзя исправить или удалить, что в некоторых случаях является проблемой (ошибочный отзыв).

5. ✅ **~~Политика UPDATE rides для RPC-функций.~~** ~~Поскольку функции `place_bid`, `close_auction_early`, `complete_trip`, `cancel_ride` используют SECURITY DEFINER, они обходят RLS при UPDATE — это правильно. Но политика `UPDATE USING (auth.uid() = creator_id)` позволяет создателю также напрямую изменять `winner_id`, `status` и `current_price` через прямой запрос к API, минуя логику RPC.~~ → Исправлено: политика `"Создатель обновляет свою поездку"` удалена. Все обновления rides идут через SECURITY DEFINER функции, которым RLS не нужен. Прямые REST UPDATE заблокированы. Миграция `20260522_fix_rides_update_policy.sql`.

### 1.3 Индексы

**Объявленные индексы (в v2):**
```sql
CREATE INDEX idx_rides_status      ON public.rides(status);

CREATE INDEX idx_rides_creator     ON public.rides(creator_id);
CREATE INDEX idx_rides_auction_end ON public.rides(auction_end_time) WHERE status = 'active';
CREATE INDEX idx_bids_ride         ON public.bids(ride_id);
CREATE INDEX idx_bids_bidder       ON public.bids(bidder_id);
CREATE INDEX idx_messages_conv     ON public.direct_messages(conversation_id);
CREATE INDEX idx_reviews_target    ON public.reviews(target_id);
CREATE INDEX idx_notif_user        ON public.notifications(user_id, is_read);
```

**Отсутствующие индексы:**

| Таблица | Поле | Почему нужен |
|---|---|---|
| `rides` | `(type, status)` составной | Feed делает WHERE type=X AND status='active' — частый запрос |
| `rides` | `winner_id` | MyTrips.tsx запрашивает WHERE winner_id = uid |
| `bids` | `(ride_id, created_at DESC)` | Каждый вызов fetchBids сортирует по created_at |
| `messages` | `(ride_id, is_read, sender_id)` | useUnreadCount делает сложный запрос по этим полям |
| `messages` | `ride_id` | Chat.tsx и Messages.tsx часто фильтруют по ride_id |
| `conversations` | `(user1_id, user2_id)` | Уже есть UNIQUE, но явный индекс ускорит поиск |
| `reviews` | `(ride_id, reviewer_id)` | Проверка существующего отзыва в TripDetail.tsx |
| `direct_messages` | `(conversation_id, is_read)` | Подсчёт непрочитанных в Conversations.tsx |
| `users` | `role` | Profile.tsx запрашивает всех водителей/пассажиров |

**Замечание:** Индексы в файле схемы не были применены через миграцию — нет уверенности, что они существуют в production-БД.

## 8. 20 идей для улучшения

### 1. Push-уведомления (браузер/PWA)
**Польза:** Пользователи получают уведомления о новых ставках и победе даже когда приложение закрыто — не пропускают аукционы.
**Сложность:** High (требует Service Worker, Push API, серверный компонент)

### 2. Избранные маршруты и уведомления о новых поездках
**Польза:** Пассажир подписывается на маршрут «Сухум → Сочи» и получает уведомление, когда появляется новая поездка — не нужно постоянно обновлять ленту.
**Сложность:** Med (таблица subscriptions + триггер на INSERT rides + push/email)

### 3. Верификация водителей через фото документов
**Польза:** Повышает доверие к платформе — пассажиры видят бейдж «Проверен» у верифицированных водителей. Актуально для региона Абхазия/Россия.
**Сложность:** Med (Supabase Storage + admin-панель для ревью)

### 4. Отзывы в обе стороны (создатель ← → победитель)
**Польза:** Сейчас только победитель оценивает создателя. Взаимные отзывы повышают качество платформы — ненадёжные пассажиры тоже получают оценки.
**Сложность:** Low (изменение логики submit_review + UI на TripDetail)

### 5. Групповое бронирование и разделение мест
**Польза:** Пассажир может забронировать несколько мест для группы (семья, компания). Водитель видит реальную заполняемость.
**Сложность:** Med (поля seats_requested в bids + изменение логики аукциона)

### 6. Карта маршрутов с интерактивными точками
**Польза:** Визуализация маршрута на карте (Яндекс.Карты/Leaflet) — пользователи видят реальное расстояние, возможные остановки и погранпереход.
**Сложность:** Med (Yandex Maps API или OpenStreetMap + geocoding)

### 7. Повторная публикация поездки (duplicate ride)
**Польза:** Если водитель регулярно ездит по одному маршруту, он может дублировать предыдущую поездку с новой датой — экономит время.
**Сложность:** Low (кнопка «Повторить» на странице поездки, pre-fill формы)

### 8. Режим «Постоянный маршрут» (daily/weekly)
**Польза:** Водители, работающие на регулярных рейсах (например, каждый день), могут указать расписание. Пассажиры видят стабильных перевозчиков.
**Сложность:** High (таблица schedules + автогенерация поездок)

### 9. Баланс и внутренние переводы
**Польза:** Оплата внутри платформы через баланс. Победитель вносит предоплату, деньги списываются при завершении. Защита от «призрачных» ставок.
**Сложность:** High (интеграция с ЮKassa/СБП + таблица transactions + escrow логика)

### 10. Чат с геолокацией водителя
**Польза:** Водитель может поделиться своей геопозицией в реальном времени через чат. Пассажир видит, где находится водитель — не нужно звонить.
**Сложность:** Med (Geolocation API + специальный тип сообщения в messages)

### 11. Рейтинг вежливости и пунктуальности
**Польза:** Разделение рейтинга на категории (пунктуальность, чистота, общение) даёт более точную оценку. Водители и пассажиры делают более осознанный выбор.
**Сложность:** Med (расширение структуры reviews + обновление UI ReviewModal)

### 12. Фильтр ленты по дате и цене
**Польза:** Сейчас поиск только по названию города. Добавить фильтры «дата отправления», «диапазон цены», «только с пересечением границы» — значительно ускоряет поиск.
**Сложность:** Low (доработка Feed.tsx без изменения БД)

### 13. Мини-профиль в ленте (hover/tap)
**Польза:** При нажатии на аватар в карточке поездки — быстрый просмотр рейтинга и последних отзывов без перехода на страницу профиля.
**Сложность:** Low (Popover/Sheet компонент с данными из creator)

### 14. История аукционов для анализа рынка
**Польза:** Пользователи могут смотреть историческую динамику цен по маршруту «Сухум → Сочи» — понять, сколько реально стоит поездка. Работает как рыночный индикатор.
**Сложность:** Med (агрегация завершённых rides по маршруту + график)

### 15. Поддержка пересадочных маршрутов
**Польза:** Маршруты с несколькими точками (например, Гагра → Сухум → Адлер). Пассажир может выйти на промежуточной остановке.
**Сложность:** High (изменение схемы rides, новая таблица waypoints)

### 16. Автоматические скидки при повторных поездках
**Польза:** Лояльные пассажиры, совершившие 5+ поездок с одним водителем, получают приоритет или скидку. Стимул строить долгосрочные отношения.
**Сложность:** Med (таблица repeat_pairs + логика в place_bid)

### 17. Telegram-бот для уведомлений и быстрых ставок
**Польза:** Пользователи, не открывающие браузер, получают уведомления в Telegram. Можно быстро принять ставку прямо из мессенджера через inline-кнопки.
**Сложность:** Med (Telegram Bot API + Supabase Edge Function webhook)

### 18. Страхование поездок (партнёрство)
**Польза:** Интеграция со страховым сервисом для поездок через границу. Опционально — доплата за страховку при создании/победе в аукционе. Уменьшает страхи при пересечении границы.
**Сложность:** High (бизнес-партнёрство + интеграция API страховщика)

### 19. Онбординг-туториал для новых пользователей
**Польза:** Первый вход после регистрации — интерактивный тур по интерфейсу: «Вот лента», «Так делается ставка», «Так выглядит чат». Снижает отток новых пользователей.
**Сложность:** Low (флаг onboarding_completed в users + react-joyride или custom flow)

### 20. Реферальная программа
**Польза:** «Пригласи друга и получи скидку на следующую поездку». Органический рост в регионе, где сарафанное радио — главный канал продвижения.
**Сложность:** Med (таблица referrals + промокоды + учёт в биллинге)
