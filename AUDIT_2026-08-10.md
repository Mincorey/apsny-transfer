### 1.1. Поездку можно опубликовать бесплатно, в обход оплаты (проверено тестом) — ✅ ИСПРАВЛЕНО 10.08.2026

> **Статус: закрыто.** Применена миграция `supabase/migrations/20260810_fix_1_1_rides_update_grants.sql`.
> Вместо белого списка колонок из патча 8.1 выбран более строгий вариант: `UPDATE` на `rides` отозван у `anon` и `authenticated` полностью — проверено, что фронтенд не выполняет ни одного прямого `.update()` на эту таблицу. Политика `rides_update_own` пересоздана с `WITH CHECK` как второй рубеж.
> Проверка на боевой базе после патча: эксплойт-1, подкрутка аукциона и массовая правка чужих поездок — `permission denied for table rides`; `publish_ride_free`, `get_trip_view`, `cancel_ride` — работают.


**Где:** RLS-политика `rides_update_own` + права на колонки таблицы `rides`.

```
rides_update_own | UPDATE | USING (auth.uid() = creator_id) | WITH CHECK: отсутствует
GRANT UPDATE на ВСЕ колонки rides для ролей anon и authenticated
```

Политика разрешает владельцу поездки менять **любые** её поля, включая `status`. Вся платная механика построена на переходе `draft → active`, который должен делать только сервер после подтверждения платежа. Но клиент может сделать это сам одним запросом:

```
PATCH /rest/v1/rides?id=eq.<мой_черновик>
{"status": "active", "auction_end_time": "..."}
```

**Проверено на боевой базе** (в транзакции с откатом): `ЭКСПЛОЙТ-1 (rides.status напрямую): ПРОШЁЛ, статус=active`.

Заодно тем же способом можно переписать `current_price`, `winner_id`, `bids_count`, `auction_end_time` — то есть **подкрутить результат аукциона**: назначить себе победителя, изменить итоговую цену, продлить или обрезать время торгов.

Триггер `trg_force_ride_draft` тут не спасает — он стоит только на `BEFORE INSERT`, а не на `UPDATE`.

**Последствие:** после включения ЮMoney — 100% потеря выручки для любого, кто откроет DevTools. Плюс манипуляция аукционом уже сегодня.

**Как чинить:** ограничить `GRANT UPDATE` только безопасными колонками + добавить `WITH CHECK`. Патч — в разделе 8.1.

### 1.2. Пользователь может накрутить себе рейтинг и счётчик поездок (проверено тестом) — ✅ ИСПРАВЛЕНО 10.08.2026

> **Статус: закрыто.** Применена миграция `supabase/migrations/20260810_fix_1_2_users_update_grants.sql` + правка `src/pages/Auth.tsx`.
> `UPDATE` отозван и выдан заново точечно на 10 колонок, которые правит интерфейс: `full_name`, `avatar_url`, `telegram`, `whatsapp`, `max`, `phone`, `show_phone`, `show_telegram`, `show_whatsapp`, `show_max`.
> Сверх пункта аудита закрыты `role`, `email`, `created_at` и `id` (последний — через `WITH CHECK`, иначе строку можно было увести на чужой uid).
> Проверка на боевой базе после патча: накрутка `rating`/`trips_count`, подмена `role`/`email`/`created_at`, увод `id` — `permission denied`; сохранение профиля, аватар, переключатели приватности, `submit_review` (рейтинг 4.7 → 4.8) — работают.
> **Связанная правка фронтенда:** `Auth.tsx` использовал `upsert`, который разворачивается в `INSERT ... ON CONFLICT DO UPDATE` и требует прав `UPDATE` на `email` и `role` — после миграции падал бы всегда. Заменён на обычный `insert`.


**Где:** `GRANT UPDATE` на колонки `users.rating` и `users.trips_count` для роли `authenticated`.

```
PATCH /rest/v1/users?id=eq.<я>
{"rating": 5.0, "trips_count": 999}
```

**Проверено на боевой базе** (откачено): `ЭКСПЛОЙТ-2 (users.rating напрямую): ПРОШЁЛ, rating=5.0`.

Рейтинг корректно пересчитывается функцией `submit_review`, но защиты «только через функцию» нет — колонка открыта на прямую запись.

**Последствие:** любой водитель рисует себе 5.0 и 999 поездок. Рейтинг — ключевой фактор выбора на вашей площадке; его подделка это репутационный и потенциально юридический риск (недобросовестная реклама).

**Как чинить:** `REVOKE UPDATE (rating, trips_count) ON users FROM authenticated, anon`. Патч — 8.2.

### 1.3. Любой авторизованный может отменить ЧУЖУЮ поездку — ✅ ИСПРАВЛЕНО 10.08.2026

> **Статус: закрыто.** Применена миграция `supabase/migrations/20260810_fix_1_3_cancel_ride_owner_check.sql`. Фронтенд не менялся.
> **Поправка к патчу 8.3:** одной проверки `creator_id <> auth.uid()` недостаточно. Сравнение с `NULL` даёт `NULL`, а не `FALSE`, поэтому при `auth.uid() = NULL` ветка `IF` не выполняется и защита молча пропускает вызов (проверено запросом к базе). Добавлена явная проверка `v_uid IS NULL` перед всеми остальными.
> Порядок проверок: авторизация → существование поездки → владелец → статус. Так чужому не сообщается статус чужой поездки.
> Проверка на боевой базе после патча: отмена чужой активной поездки — `Отменить поездку может только её создатель` (статус остался `active`); вызов без авторизации — `Требуется авторизация`; владелец отменяет свою — работает, уведомление участнику ставки уходит.


**Где:** функция `public.cancel_ride(p_ride_id uuid)`, права `authenticated=EXECUTE`.

В теле функции **нет ни одной проверки прав**:

```sql
SELECT * INTO v_ride FROM public.rides WHERE id = p_ride_id FOR UPDATE;
IF NOT FOUND THEN RAISE EXCEPTION 'Поездка не найдена'; END IF;
IF v_ride.status != 'active' THEN RAISE EXCEPTION '...'; END IF;
-- ↓ проверки "это моя поездка?" НЕТ
UPDATE public.rides SET status = 'cancelled', cancelled_at = now() WHERE id = p_ride_id;
```

Функция `SECURITY DEFINER`, то есть выполняется от имени владельца БД — RLS её не ограничивает.

**Последствие:** один скрипт в цикле по всем `id` из ленты кладёт весь сервис. Все активные аукционы отменяются, всем участникам летят уведомления «Поездка отменена».

**Как чинить:** добавить `IF v_ride.creator_id <> auth.uid() THEN RAISE EXCEPTION ...`. Патч — 8.3.

### 1.4. Любой авторизованный может досрочно закрыть ЧУЖОЙ аукцион — ✅ ИСПРАВЛЕНО 10.08.2026

> **Статус: закрыто.** Применена миграция `supabase/migrations/20260810_fix_1_4_finish_auction_service_only.sql`. Фронтенд не менялся — он `finish_auction` не вызывает вообще.
> Сделано два рубежа вместо одного `REVOKE` из патча 8.3:
> 1. `REVOKE ALL` у `public`, `anon`, `authenticated` — осталось `{postgres, service_role}`. Cron (jobid 1, 3) работает от `postgres`; `close_expired_auctions`, `process_expired_auctions` и `get_trip_view` — `SECURITY DEFINER` от `postgres`, поэтому вложенный вызов прав вызывающего не требует.
> 2. Внутрь функции добавлена проверка `auction_end_time > now() → {"success": false, "reason": "auction_not_expired"}`. Страховка от повторной выдачи `EXECUTE` — такая регрессия уже была с `rides_update_own`. Безопасна: все три легальных вызывающих и так отбирают только истёкшие, а `close_auction_early` эту функцию не вызывает.
> Проверка на боевой базе после патча: прямой вызов — `permission denied for function finish_auction`; `get_trip_view` на истёкшем — `booked` с победителем; `close_auction_early` владельцем — работает; cron `close_expired_auctions` — отрабатывает.
> **Не входит в этот патч:** победитель по-прежнему определяется как автор последней по времени ставки, а не лучшей по цене — это пункт 2.3.


**Где:** функция `public.finish_auction(p_ride_id uuid)`, права `authenticated=EXECUTE`.

Функция задумана как служебная (её дёргает cron), но выдана обычным пользователям и не проверяет, кто зовёт. Вызов `finish_auction(<чужая поездка>)` немедленно закрывает торги и объявляет победителем текущего лидера.

Схема злоупотребления: сделал ставку → сразу вызвал `finish_auction` → выиграл аукцион по своей же цене, не дав другим перебить.

Для сравнения, «правильный» аналог `close_auction_early` проверку имеет:
```sql
IF v_ride.creator_id != auth.uid() THEN RAISE EXCEPTION 'Только создатель поездки может закрыть аукцион'; END IF;
```

**Как чинить:** `REVOKE EXECUTE ON finish_auction FROM authenticated`. Патч — 8.3.

### 1.5. Можно поставить ставку от имени другого пользователя — ✅ ИСПРАВЛЕНО 10.08.2026

> **Статус: закрыто.** Применена миграция `supabase/migrations/20260810_fix_1_5_accept_current_price_auth.sql` + правка `src/pages/TripDetail.tsx`.
> **Найден третий пробел, которого нет в аудите.** Сверка с `place_bid` (7 проверок против 3) показала, что отсутствовал ещё и запрет двух ставок подряд. Без него участник мог вызывать функцию сколько угодно раз: накручивать `bids_count`, спамить создателя уведомлениями и бесконечно удерживать позицию последней ставки — а именно по ней `finish_auction` назначает победителя. Проверка добавлена по образцу `place_bid`.
> Итоговый набор проверок: авторизация → поездка найдена → статус `active` → торги не истекли → не своя поездка → не две ставки подряд.
> **Порядок выката обязателен: сначала миграция, потом фронтенд.** Параметр `p_bidder_id` не удалён, а сделан необязательным (`default null`) и игнорируется — иначе новый фронтенд, не отправляющий его, не нашёл бы функцию в старой базе. Обе комбинации проверены на боевой базе. Удалить параметр совсем можно отдельной миграцией позже.
> Проверка на боевой базе после патча: подстановка чужого `p_bidder_id` — ставка записывается на вызывающего; две ставки подряд, ставка после окончания торгов, ставка на свою поездку, вызов без авторизации — отклоняются; обычное согласие с ценой — работает.


**Где:** функция `public.accept_current_price(p_ride_id uuid, p_bidder_id uuid)`, права `authenticated=EXECUTE`.

Функция принимает `p_bidder_id` **параметром** и нигде не сверяет его с `auth.uid()`:

```sql
IF v_ride.creator_id = p_bidder_id THEN RAISE EXCEPTION 'Нельзя делать ставку на свою поездку'; END IF;
INSERT INTO public.bids (ride_id, bidder_id, amount) VALUES (p_ride_id, p_bidder_id, v_ride.current_price);
```

Фронтенд честно подставляет свой `userId` (`TripDetail.tsx:304`), но запрос легко подменить. Дополнительно функция **не проверяет `auction_end_time`** — можно «согласиться с ценой» уже после окончания торгов.

**Последствие:** ставки от чужого имени → чужая победа в аукционе, чужие уведомления, испорченная история. `place_bid` (основная функция ставок) сделана правильно и все проверки имеет — тем заметнее пробел здесь.

**Как чинить:** убрать параметр `p_bidder_id`, брать `auth.uid()`, добавить проверку времени. Патч — 8.4.

## 7. Чеклист переноса на VDS

Вы переносите **и приложение, и базу**. Это два очень разных по сложности переезда — фронтенд это статика, а Supabase это связка из 8+ сервисов. Разберём по шагам.

### 7.1. Что вообще придётся поднять

Supabase — это не «просто Postgres». Ваш проект использует:

| Сервис Supabase | Где используется в проекте | Обязателен? |
|---|---|---|
| PostgreSQL 17 | вся БД | да |
| GoTrue (Auth) | регистрация, вход, `auth.uid()` в каждой RLS-политике | да |
| PostgREST | **все** запросы `supabase.from(...)` и `supabase.rpc(...)` | да |
| Storage | аватары, фото машин (`Profile.tsx`) | да |
| Edge Functions (Deno) | `yoomoney-webhook` | да (или переписать на свой backend) |
| Realtime | публикация настроена миграцией `20260605_realtime_publication.sql` | сейчас не используется фронтом (лента опрашивает по таймеру) |
| `pg_cron` | 5 регулярных задач | да |
| `pg_net` | Telegram-уведомления (`tg_notify`) | да |
| Vault | хранит токен Telegram-бота | да |

**Рекомендация:** ставьте официальный self-hosted Supabase через `docker compose` (репозиторий `supabase/supabase`, папка `docker`). Собирать это вручную из отдельных компонентов — путь к неделям отладки RLS и JWT.

### 7.2. Требования к VDS

- Минимум **4 vCPU / 8 ГБ RAM / 80 ГБ SSD**. На 2 ГБ Supabase-стек не взлетит.
- Ubuntu 22.04 / 24.04 LTS, Docker + Docker Compose v2.
- Публичный IP, открытые 80/443.
- **Юрисдикция:** проект работает с ПДн граждан РФ (ФИО, телефон, email) → по 152-ФЗ сервер должен быть **в России**. Сейчас БД в регионе `ap-southeast-2` (Австралия) — это уже несоответствие, и переезд его как раз исправляет.

### 7.5. Конфигурация nginx (замена `vercel.json`)

`vercel.json` делает ровно одно — отдаёт `index.html` на любой путь (SPA-роутинг). На nginx:

```nginx
server {
    listen 443 ssl http2;
    server_name apsny-transfer.ru;

    root /var/www/apsny/dist;
    index index.html;

    # SPA-fallback — аналог rewrites из vercel.json
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Хешированные ассеты — кэш навсегда
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # index.html не кэшировать никогда
    location = /index.html {
        add_header Cache-Control "no-cache, must-revalidate";
    }

    gzip on;
    gzip_types text/css application/javascript application/json image/svg+xml;

    # Заголовки безопасности — сейчас их нет вообще
    add_header X-Frame-Options            "SAMEORIGIN"        always;
    add_header X-Content-Type-Options     "nosniff"           always;
    add_header Referrer-Policy            "strict-origin-when-cross-origin" always;
    add_header Permissions-Policy         "geolocation=(), microphone=(), camera=()" always;
    add_header Strict-Transport-Security  "max-age=31536000; includeSubDomains" always;
}
```

### 7.6. Обязательное после переезда

- **Бэкапы.** В Supabase они были автоматические. На VDS их нет — настройте `pg_dump` по cron с выгрузкой в отдельное хранилище (не на тот же диск!) и **проверьте восстановление**. Бэкап, который не восстанавливали, — это не бэкап.
- **Мониторинг.** Место на диске, живость контейнеров, доступность вебхука ЮMoney. Если вебхук ляжет — деньги придут, а поездки не опубликуются, и вы узнаете об этом от пользователей.
- **SSL:** certbot + автопродление.
- **Фаервол:** наружу только 80/443 и SSH. Порт Postgres 5432 **не открывать в интернет**.
- **Часовой пояс.** `publish_ride_paid` формирует квитанцию через `now() at time zone 'Europe/Moscow'`, а `auto_complete_expired_rides` считает `(departure_date + departure_time)::timestamptz` — это использует `TimeZone` сессии. Выставьте на сервере и в Postgres единый TZ, иначе поездки начнут завершаться не в то время.
- Первым делом после переезда прогнать чеклист из `ПРОВЕРИТЬ.md`.

### 8.3. Проверка владельца в `cancel_ride`, закрыть `finish_auction` (закрывает 1.3, 1.4)

```sql
CREATE OR REPLACE FUNCTION public.cancel_ride(p_ride_id uuid)
RETURNS jsonb LANGUAGE plpgsql SECURITY DEFINER SET search_path TO 'public','pg_temp'
AS $$
DECLARE v_ride RECORD;
BEGIN
    SELECT * INTO v_ride FROM public.rides WHERE id = p_ride_id FOR UPDATE;
    IF NOT FOUND THEN RAISE EXCEPTION 'Поездка не найдена'; END IF;

    IF v_ride.creator_id <> auth.uid() THEN            -- ← добавленная проверка
        RAISE EXCEPTION 'Отменить поездку может только её создатель';
    END IF;

    IF v_ride.status != 'active' THEN RAISE EXCEPTION 'Можно отменить только активные поездки'; END IF;

    UPDATE public.rides SET status='cancelled', cancelled_at=now() WHERE id = p_ride_id;

    INSERT INTO public.notifications (user_id, type, title, body, ride_id)
    SELECT DISTINCT bidder_id, 'ride_cancelled', 'Поездка отменена', NULL, p_ride_id
    FROM public.bids WHERE ride_id = p_ride_id;

    RETURN jsonb_build_object('success', true, 'status', 'cancelled');
END; $$;

-- finish_auction — служебная, её зовёт только cron и get_trip_view
REVOKE EXECUTE ON FUNCTION public.finish_auction(uuid) FROM anon, authenticated;
```

### 8.4. Ставка только от своего имени (закрывает 1.5)

```sql
CREATE OR REPLACE FUNCTION public.accept_current_price(p_ride_id uuid, p_bidder_id uuid DEFAULT NULL)
RETURNS jsonb LANGUAGE plpgsql SECURITY DEFINER SET search_path TO 'public','pg_temp'
AS $$
DECLARE
    v_ride   RECORD;
    v_bidder uuid := auth.uid();          -- ← берём из сессии, параметр игнорируем
BEGIN
    IF v_bidder IS NULL THEN RAISE EXCEPTION 'Требуется авторизация'; END IF;

    SELECT * INTO v_ride FROM public.rides WHERE id = p_ride_id FOR UPDATE;
    IF NOT FOUND THEN RAISE EXCEPTION 'Поездка не найдена'; END IF;
    IF v_ride.status != 'active' THEN RAISE EXCEPTION 'Аукцион уже завершён'; END IF;

    IF v_ride.auction_end_time IS NOT NULL AND v_ride.auction_end_time < now() THEN
        RAISE EXCEPTION 'Время приёма ставок истекло';   -- ← добавленная проверка
    END IF;
    IF v_ride.creator_id = v_bidder THEN
        RAISE EXCEPTION 'Нельзя делать ставку на свою поездку';
    END IF;

    INSERT INTO public.bids (ride_id, bidder_id, amount) VALUES (p_ride_id, v_bidder, v_ride.current_price);
    UPDATE public.rides SET bids_count = bids_count + 1, last_bid_at = now() WHERE id = p_ride_id;

    INSERT INTO public.notifications (user_id, type, title, body, ride_id)
    VALUES (v_ride.creator_id, 'new_bid', 'Водитель согласился с ценой!',
            'Ставка: ' || v_ride.current_price || ' ₽', p_ride_id);

    RETURN jsonb_build_object('success', true, 'amount', v_ride.current_price);
END; $$;
```
Фронтенд менять не обязательно — параметр стал необязательным и просто игнорируется.
